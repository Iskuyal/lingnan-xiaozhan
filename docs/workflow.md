# 比赛工作流

## 阶段与完成条件

本文件描述赛事总体里程碑。实际开发采用 [开发阶段](development-phases.md) 的 P0–P6 编号，功能与技术边界见 [开发规格](development-spec.md)。按验收推进，有时间即可制作；以下日期仅作比赛倒排参考。

以下日期为内部建议目标，按原文省赛 2026-11-18 截止倒排，并非官方新增要求。官方日程变更后同步调整。

| 阶段 | 内部目标 | 工作与输出 | 完成条件 |
| --- | --- | --- | --- |
| 0 规则与资源确认 | 09-20 | 核实时间冲突、组别、队员、微信及 AI 资源 | 负责人、资源缺口和官方待答问题均有记录 |
| 1 选题验证 | 09-27 | 比较候选场景、获取真实需求证据、确认作品定位 | 确定目标用户、核心问题和 AI 价值；更新 CONTEXT |
| 2 MVP 与技术验证 | 10-04 | 明确范围、用户流程、页面草图、技术方案和关键接入验证 | 核心路径可实现，AI/微信关键依赖经验证，任务有验收标准 |
| 3 核心闭环实现 | 10-25 | 完成前端、服务端、AI 接入和必要微信能力 | 用户核心流程端到端可运行，关键测试通过 |
| 4 用户验证与完善 | 11-08 | 真机或模拟器测试、AI 评估、用户反馈、修复与运营设计 | 演示阻断问题关闭，失败场景有反馈，评估和用户证据可查 |
| 5 材料冻结 | 11-15 | 完成七项说明、录屏、截图、源码和体验说明 | 全部提交清单检查完成，参赛包可解压并按说明复现 |
| 6 提交归档 | 11-17 | 人工核对入口、提交并保存回执 | 已收到提交成功凭证，归档提交包与对应 Git 版本 |

国赛流程在晋级和官方日期确认后执行：评审反馈 → 改进任务 → 回归验证 → 更新材料与历史说明 → 重新提交归档。

## 日常执行

1. 从 Issues 选择无未完成依赖的任务，确认负责人、范围及验收标准。
2. 新建短期分支，如 `docs/competition-setup`、`feat/<主题>`、`fix/<主题>`。
3. 先给出计划和验证方法；实现最小完整结果。业务 bug 先复现，功能验证覆盖用户可观察行为。
4. 提交 PR，关联 Issue，说明改动、验证命令和结果；界面变更附截图，AI 行为变更附样例及评估。
5. 审查通过并满足验收条件后合并到 `main`，关闭任务，更新成果证据和相关文档。

项目初始化可直接提交 `main`。后续不引入长期 develop 分支，避免小团队额外维护成本。
P1 已提供类型检查、构建、页面行为测试和 GitHub Actions，后续业务测试随功能加入。开发者工具及真机验证分别记录，CI 通过不代替实际运行验收。

## 任务与依赖

- 分流规则见 [标签配置](agents/triage-labels.md)。
- 信息缺失标记 `needs-info`；需人工决定选题、配置账号或确认赛事信息时标记 `ready-for-human`。
- 明确依赖，用 `Blocked by: #编号` 或 GitHub 原生依赖表达；完成条件未满足时不关闭任务。
- 每周回顾核心流程、评分证据和截止风险，缩减低价值范围，保证可演示与材料完整。

## 验证与证据

技术方案确定时给出核心流程成功、空数据、无权限、网络或模型失败等验收案例，以及适用的性能和成本预算。
AI 评估使用固定的代表性输入，记录预期、实际输出、正确性或可用性判定、耗时及成本；需要知识依据时记录来源。
成果记录注明版本、环境、步骤、实际结果和日期。文档、截图与视频应对应最终提交版本；模板和模拟结果必须标明状态。

## 发布与提交

按 [提交清单](submission.md) 检查后创建版本标签并制作参赛包。包内提供可复现源码和配置说明，凭据由运行环境注入。
演示用账号按实际需要单独提供最小权限测试账号；生产密钥、个人数据、构建缓存和依赖目录不放入参赛包。
由负责人在实际比赛入口完成提交，保存成功回执。GitHub push 不代表完成比赛提交。
