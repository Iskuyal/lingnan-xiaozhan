# AI 稳定性探针与审核超时修复（2026-10-29）

## 结论摘要

1. **初始故障点不是业务模型**：10 次真实调用 9 成 1 败，唯一失败在输出内容安全——模型 4632ms 已返回，第三方审核超过 **6000ms** 被 fail-closed 拒绝。
2. **控制台配置与运行实例不一致**：负责人确认控制台 `AI_SAFETY_TIMEOUT_MS=30000`、`AI_TOTAL_DEADLINE_MS=40000`，且其它环境变量（个人日额度 60、单价 0.25）在返回中生效；但失败 `detail` 始终显示 `请求超时（6000ms）`，与线上 `ai/config.js` 逐字节一致 ⇒ 运行实例实际用的是**代码默认值 6000**，不是控制台值。具体为何该变量未被实例读取，端上无法进一步确认（可能为变量名隐藏字符或配置未随版本生效）；**代码不再依赖它**。
3. **修复已部署并验证**：审核超时默认值改为按提供方区分——`wechat` 6000、第三方（openai/anthropic）30000（仍受总截止约束）。部署后 `moderateText` 的失败/成功记录明确出现 `请求超时（30000ms）`，证明新默认值生效。
4. **第三方审核服务当晚严重抖动**：同一时段审核从 2–3s 到 >30s 不等（2000 字 2.98s 成功、6000 字 8.5s 成功、也出现过 30s 超时），这是服务方尾部延迟，不是本项目的超时设置能根治的。
5. **微信官方通道可用且快**：`probe` 动作两条接口 `errcode 0`（562ms / 482ms）。**建议评委演示期间把 `AI_SAFETY_PROVIDER` 临时切回 `wechat`**（免费、快，未上架小程序约 100 次检测/天），演示后再评估是否切回第三方。

## 边界

- 原生模拟器 + 直发云函数；不是真机，也不是页面端到端时延；未做回答事实正确性评分。
- 第三方审核抖动的根因在服务方，本记录只证明「超时上限已不再错误地停在 6000」与「微信通道可回退」，不证明第三方 SLA。
- 本次改动只影响审核超时默认值；未改模型、审核提供方、额度或密钥。
