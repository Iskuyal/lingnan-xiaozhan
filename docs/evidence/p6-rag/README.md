# RAG 语料可行性实测（PoC 第一轮）

实测日期：2026-09-19 ｜ 结论：**否定**——官网现有语料不足以支撑「校园通知与办事指引问答」
对应执行票：[Ticket 10](../../tasks/tickets/10-campus-rag-qa.md)（关卡 4「是否先做 PoC」的产出）

---

## 一、为什么要先量语料

Ticket 10 的能力承诺完全取决于「官网到底有多少可检索的正文」。2026-09-18 的两轮静态实测只回答了「条目指向哪里」（教务处 108 条全是公众号外链、制度文件是 PDF），**没有回答「有正文的那些，正文有多长、够不够问」**。本轮把 9 个拟入库栏目完整抓下来量了一遍。

**关键点：这一轮不调用任何模型**，纯抓取 + 项目自己的解析器（`dist/cloudfunctions/newsSync/parse.js`），因此语料与云端入库结果同源。

## 二、数字

抓取范围：Ticket 10 选定入库的 9 个栏目（团委通知公告 + 保卫 3 + 质量监控 + 教务处教学运行 + 3 个书院），共 31 个列表页。

| 项 | 数量 |
| --- | --- |
| 列表条目总数 | 245 |
| **可用（解析出正文）** | **168 篇** |
| 图片正文（`div.conTxt` 里只有 `<img>`，是海报扫描） | **66 篇** |
| 无正文（只有标题与署名） | 10 篇 |
| 站外（公众号外链，项目已定不入库） | 1 篇 |
| **可用语料总字数** | **49,321 字**（平均 294 字/篇） |

长度分布（可用 168 篇）：

| 正文长度 | 篇数 |
| --- | --- |
| 0–200 字 | **97** |
| 200–500 字 | 52 |
| 500–800 字 | 8 |
| 800–1500 字 | 5 |
| 1500 字以上 | 6 |

**≥500 字的只有 19 篇**（涉及 6 个栏目），≥800 字的 11 篇，≥1500 字的 6 篇。

## 三、为什么这么薄

三类"看着有、读不了"的内容，各自原因不同，且都不是解析缺陷：

1. **图片正文 66 篇（占 27%）**：`div.conTxt` 里是一串 `<img src="/upload/tw/.../xxx.png" width="1660" height="2359">`，正文是**通知海报的扫描图**。解析器返回空段落是**正确行为**——页面上确实没有文字。例：`/tw/djxf/tqsd/content_26927`（2025 年科技文化节通知，连续 8 张图）。
2. **制度文件只有 PDF**：信息公开网的学籍 / 奖助 / 申诉办法，页面正文区没有文字，正文由 `a[href$=".pdf"]` 经 JS 塞进 pdf.js 的 iframe（Ticket 10 已记录）。
3. **95 篇 ≤300 字的是公示与短通知**：正文常只有「根据……经研究决定……现予公示」加附件表，例如 `关于广东岭南职业技术学院2026年上半年拟入团发展对象名单的公示`（367 字）。

## 四、补充实测：PDF 制度文件也没有文字层（2026-09-19）

路径 C 的前提是「PDF 抽文本 + 图片通知 OCR」。抽了一份真实的制度 PDF 检查（信息公开网「广东岭南职业技术学院学籍管理办法」的附件）：

| 检查项 | 结果 |
| --- | --- |
| 文件大小 | 2,561,634 字节（2.5 MB） |
| `/Font` 标记 | **不存在** |
| `/Image` 标记 | 存在 |
| `/Subtype /Type0`（CID 中文字体） | 不存在 |
| stream 块 / 成功 inflate | 25 / 12 |
| 文本算子 `Tj`/`TJ` | 9 处（集中在少量非正文流） |
| 图片算子 `/Image`、`Do` | 19 处 |

**结论：制度文件 PDF 是纯扫描件，没有文字层**，「抽文本」这一步不存在——**PDF 这一半同样要 OCR**。于是路径 C 收敛成一件事：**OCR**（66 篇图片通知 + 约 60 份扫描件 PDF），而不是两条技术链路。

两条由此而来的工程事实：

1. **PDF 不能直接丢给模型**：2.5 MB 的单份扫描件超出图片接口限制，必须走「PDF 识别」类接口，或先转页图再逐页识别。
2. **入库是一次性离线批处理，不必挤进云函数**：66 + 60 份文档的 OCR 可以本机脚本跑完再写库，绕开云函数 20 秒 / 256MB 的限制；只有**增量**新文章才需要考虑自动化。这与 Ticket 05（用户实时上传截图，受时延约束）是两种节奏，别混在一起设计。

复现：`node artifacts/rag-poc/check-pdf.cjs <pdf 路径>`（无依赖：读字节 → inflate 内容流 → 数文本/图片算子）。

## 五、这对方向意味着什么

**按原计划（只收官网 A 类 HTML 正文）做「校园通知与办事指引问答」不成立**：语料 4.9 万字、其中 58% 的篇目不足 200 字，能撑起问答的实质文档只有十几篇，且主题分散在挑战杯、台风、户口迁移、校区交通管理上——学生真会问的问题（怎么办转专业、奖助学金怎么评、四六级什么时候报名、图书馆几点开门）在这份语料里**基本没有答案**。

三条可选路径（**需负责人定，票内关卡 1 需重开**）：

| 路径 | 做法 | 语料规模（估） | 代价 |
| --- | --- | --- | --- |
| **C. 先做 OCR / 文档解析这条共用链路**（本轮推荐） | 图片通知 66 篇 OCR 出文字 + PDF 制度 60 篇抽文本（扫描件再 OCR） | 约 300 篇 / **20–30 万字**，且**恰好包含学籍、奖助、申诉这些学生真会问的内容** | 一条新链路，但**同时救 Ticket 05**（课表截图识别现在卡在模型超时；先 OCR 出文字、模型只做结构化，token 与时延大幅下降），且 OCR 是赛题「建议技术实现」里点名的业务能力 |
| A. 改做「校园资讯问答」 | 用校园动态 1252 篇（约 165 万字，**唯一有量的文本源**） | 约 1400 篇 | 语料是事后报道（AI 资讯实测：8/8 无学生行动项），对"我该怎么办"类问题价值低，场景落地分难拿 |
| B. 砍掉 RAG | 把 AI 分数押在既有三落点 + 评估证据上 | — | 赛题在 AI 能力里点名 RAG，等于放弃该项 |

## 六、复现方式

```powershell
npm ci
npm run build                                   # 产出 dist/cloudfunctions/newsSync/parse.js
node scripts/rag-poc.cjs crawl                  # 抓语料快照 → artifacts/rag-poc/corpus.json
node artifacts/rag-poc/corpus-stats.cjs         # 长度分布（本文表格即由它汇总）
node scripts/rag-poc.cjs recall                 # 纯本地检索评估（题库见 docs/evidence/p6-rag/questions.json）
node scripts/rag-poc.cjs answer                 # 模型阶段（需 AI_BASE_URL / AI_API_KEY / AI_MODEL）
```

`recall` 与 `answer` 两个子命令已就绪但**本轮未执行**：语料可行性已经在出题之前被长度分布否决，先花模型调用费去测一个语料撑不起的问题域不划算。语料问题一旦按路径 C 解决，这两个命令可直接复用。

抓取遵守官网 WAF 的「每秒 ≤1 个页面请求」（间隔 1.4 秒），约 290 次请求耗时约 7 分钟；快照与中间产物都在 `artifacts/`（已 gitignore，不进仓库）。
