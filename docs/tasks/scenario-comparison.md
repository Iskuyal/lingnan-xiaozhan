# 候选场景对比与选题建议

对应 GitHub Issue #2「验证候选场景并确定作品选题」。整理日期：2026-09-18。

## 决策记录（2026-09-18）

**负责人已确认采纳第五节建议：保留 A（信息整合）作底座，把 AI 能力押在 B（诉求归纳与进度追踪）上。**

负责人同时明确：**这只是产品的其中一个功能，后续会继续添加内容。** 这条约束影响架构，不只是选题：

- 模块边界要预留扩展位，不要把首页和导航写死成「资讯 / 部门 / 课表」三格；
- 资讯链路（云函数 + 数据库 + 页面框架）应作为**可复用的基础设施**看待，新功能优先复用同一套云端读写与来源标注方式，而不是每加一个功能就新起一套；
- 数据来源与「不编造」纪律按现有约定延续（每条内容带来源与核查日期）。

本节以下内容为决策依据的原文，保留以便回溯。

## 一、硬约束（不可选的部分）

| 约束 | 内容 | 来源 |
| --- | --- | --- |
| 主题方向 | AI 赋能校园生活 | 赛题文档主题方向表；`CONTEXT.md` 已确定 |
| 参赛范围 | 校园服务（办事大厅、学习打卡、活动报名、图书借阅、课程与考试助手） | 赛题文档参赛范围表 |

| 其他权重 | 技术实现 25%、创新设计 20%、场景落地与商业闭环 15%、产品体验与用户增长 10%、完整性与材料质量 10% | 同上 |
| 已有资产 | P1 首页、P2 学生部门、P3-1 官网资讯云端链路已实现并通过开发者工具验收 | `docs/development-phases.md` |
| 最大未知 | 教务课表接入可行性（P4-A 未做）；AI 具体功能（P5-A 未定） | 同上 |

**关键判断依据**：AI 能力融合占 20 分且明确要求「在业务流程中真实发挥作用」。一个只能展示官网文章的资讯页，AI 贡献接近于零；把摘要贴上去也不构成「真实发挥作用」。所以选题的核心问题不是「做什么模块」，而是**AI 在哪条流程里做一件不用 AI 就做不到的事**。

## 二、可核查的需求证据（全部来自校方公开报道）

以下证据均来自学校官网已发布文章，可直接引用并附 URL。这也是本项目相较其他参赛作品的优势：**证据是一手的、本校的、可点开核对的**。

### 2.1 学生诉求的收集与归纳（校长接待日第四期，2025-11-20）

来源：<https://lnc.edu.cn/tw/djxf/djhd/content_27006>

> 前期通过校学生会问题反馈渠道，共收集到 **56 条学生诉求**，涵盖食堂餐饮、设施维护、生活保障等多个领域，**经梳理整合为 15 个核心问题**。

诉求覆盖六大领域（原文列举）：住宿服务（热水、阳台安全、施工噪音、报修、隔音）、餐饮服务（菜价公示、菜品迭代）、公共设施与环境（厕所门、贩卖机保质期、路灯）、交通停放（接驳车、自行车棚）、医卫与商业（校医室药价、外卖柜）、校内兼职（用工标准、工时、试用期薪资、权益追责）。

**这条证据同时说明两件事**：诉求量真实存在（56 条）；**「56 条 → 15 个核心问题」的归纳整理目前靠人工**，而这正是大模型最擅长的事。

### 2.2 学生没有自助查询进度的渠道

同文结尾：

> 【后续提醒】你的问题，这样查进度：1. 校学生会权益部将持续跟踪……

文章给不出一个学生可以自己查询的入口，只能说「权益部将持续跟踪」。**「提交之后不知道进展」是公开报道本身暴露的缺口。**

### 2.3 学生自己提出的改进方向（校长接待日第五期，2025-12-18）

来源：<https://lnc.edu.cn/tw/djxf/djhd/content_27037>

五条核心建言：职业规划课「企业化」（企业行、见习岗位、企业导师讲座）、学术资源「用得会」（文献检索咨询岗、数据库培训）、实践基地「接地气」、学风活动「品牌化」（一月一主题学风月历、纳入第二课堂系统）、学习互助「全覆盖」（国奖学生讲师团入驻社区晚自习答疑）。

## 三、三个候选场景

### 候选 A：校园信息整合（当前方向）

把官网资讯、学生组织、课表整合到一个入口。

| 维度 | 评估 |
| --- | --- |
| 目标用户 | 全校学生（泛） |
| 现有流程 | 跨 20 个栏目翻找；课表需登录教务系统；公众号文章无从检索 |
| 需求证据 | 2.5 的量化证据；无学生直接诉求的原文引用 |
| 数据来源 | 官网（**已跑通**，云端已入库）；课表待 P4-A 验证 |
| AI 落点 | 摘要、分类、检索问答（RAG）。**但用户现有流程里 AI 不是必需**：不装 AI 也能看文章 |
| 微信触达 | 小程序本身；订阅消息可用但无强场景 |
| 实现成本 | 低（P1/P2/P3-1 已完成） |
| 主要风险 | ① 课表接入很可能失败，届时模块缩水；② **AI 贡献弱，「AI 能力融合」20 分难以拿高分**；③ 创新性一般，同类校园信息小程序多 |

### 候选 B：诉求 / 提案的提交与进度追踪闭环

学生提交诉求或提案，系统归纳归类、推送给对应组织、公开进度。

| 维度 | 评估 |
| --- | --- |
| 目标用户 | 提交方：全校学生；处理方：校学生会权益部、后勤管理处 |
| 现有流程 | 校长接待日现场提、提案大赛参赛、找权益部反馈；**提交后无自助查询入口**（证据 2.2） |
| 需求证据 | **最强**：56 条诉求 / 15 个核心问题（2.1）、9 支决赛队伍与真实提案题目（2.4）、权益部持续跟踪但无查询渠道（2.2） |
| 数据来源 | **冷启动语料已公开可用**：官网已发布的历次接待日诉求、提案大赛题目、通知公告 |
| AI 落点 | **强且不可替代**：诉求自动归类与相似合并（人工做的「56→15」）、答复草稿生成、进度摘要、基于既有处理记录的 RAG 问答 |
| 微信触达 | **强**：小程序提交 + 订阅消息推送进度变更是微信生态的原生能力，也是「用户增长设计」10 分的落点 |
| 实现成本 | 中：需表单、审核流、通知、状态机；不含 AI 也能做，加 AI 才有差异化 |
| 主要风险 | **需要真实处理方配合**。若只有学生端、无人处理，闭环在评审眼中不成立。缓解办法：冷启动只用公开的既有诉求做演示数据，把「处理方」做成可选的接入方而非前置依赖 |

### 候选 C：学业与成长 AI 助手

对话式学业规划、资源检索、朋辈经验问答。

| 维度 | 评估 |
| --- | --- |
| 目标用户 | 有学业/职业迷茫的学生 |
| 现有流程 | 靠学长学姐分享（「七杯奶茶」活动）、辅导员、自己摸索 |
| 需求证据 | 中等：第五期接待日 5 条建言（2.3），含「学习互助全覆盖」「学术资源用得会」 |
| 数据来源 | **缺**：本校学业数据（培养方案、课程、教师答疑）没有公开可抓的来源 |
| AI 落点 | 强（对话、规划、检索） |
| 微信触达 | 中：小程序对话；无强推送场景 |
| 实现成本 | 低到中（接大模型即可） |
| 主要风险 | **同质化最严重**：与市面通用 AI 助手难以区分，缺本校数据护城河，创新设计 20 分难拿；且「校园服务」范围内的数据支撑最薄弱 |

## 五、建议

**建议：保留 A 作为底座，把 AI 能力押在 B 上。**

理由：

1. **A 已经跑通，是「完整性与材料质量」10% 和技术实现 25% 的保底**——首页、部门、资讯云端链路都已验收，不推倒重来。
2. **B 的需求证据是三个候选里唯一由校方公开报道直接支撑的**，而且是学生自己的诉求，不是我们推测的。
3. **B 里的 AI 真的不可替代**：把 56 条自然语言诉求归并成 15 个核心问题、判断重复诉求、生成答复草稿——这是大模型的强项，也正是目前人工在做的事。这直接对应「在业务流程中真实发挥作用」。
4. **B 不依赖外部方即可演示**：冷启动语料用官网已公开的历次诉求与提案，评审能看到真实数据跑出真实归纳结果。「处理方接入」做成可选能力，不作为前置依赖，规避最大风险。
5. **C 不建议作为主线**：数据来源最薄弱、同质化最严重，拿不到创新分。
