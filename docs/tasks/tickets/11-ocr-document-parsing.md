# 11：OCR / 文档解析共用链路（图片通知与扫描件 PDF 入库）

**What to build:** 一条能**从图片里取出文字**的链路，服务于两处：① 把官网里「只有海报扫描图」的通知和「纯扫描件」的制度 PDF 变成可检索文本，补足 [Ticket 10](10-campus-rag-qa.md) 的语料；② 给 [Ticket 05](05-timetable-screenshot-import.md) 的课表截图识别做前置（先 OCR 出文字，再让模型只做结构化，绕开「模型输出 token 太慢」的硬约束）。

**Blocked by:** 无。前置实测已完成（见下）。**依赖外部服务的开通**（OCR 服务选型是关卡 1）。

**Status:** in-progress（2026-09-19 创建；关卡 1、2 已定——**腾讯云 OCR**、**先做图片通知**；**输入清单与调用脚本已就绪，只差腾讯云密钥**；余关卡 3、4、5 待确认）

**来源：** [Ticket 10](10-campus-rag-qa.md) 的 PoC 第一轮给出否定结论——官网可入库正文只有 168 篇 / 4.9 万字，58% 的篇目不足 200 字，撑不起问答。负责人选定「先做 OCR / PDF 共用链路」这条补救路径。完整数字见 [语料可行性实测](../../evidence/p6-rag/README.md)。

**跑法（密钥配好之后）**：

```powershell
node scripts/ocr-backfill.cjs plan        # 看清单与调用量（现在就能跑）
node scripts/ocr-backfill.cjs run --limit 3   # 先试 3 篇，验证质量与计费
node scripts/ocr-backfill.cjs run             # 跑完剩余全部
```

**已知质量风险（跑之前先认下来）**：这些通知是**多栏设计稿式的海报**，OCR 的阅读顺序可能错乱。这一点已经**按坐标重排**处理（见上表；重排前的接口原顺序也留在结果里，抽检时两个都能看），但重排是启发式的，**仍然必须人工抽检**：

- 若抽检发现顺序仍错乱，先改 `scripts/lib/ocr-order.cjs` 的规则并用存量坐标**离线重算**（不必再调接口）；
- 若改规则也救不回来，**这条路径按验收标准判为不成立**，回到 Ticket 10 的另两条路；
- **抽检不达标就不要入库**——OCR 文本一旦混进检索语料，问答会答错而且看起来很像对的。

抽检方法：结果 JSON 里每篇都有 `text`（接口原顺序）与 `orderedText`（重排后）两种文本，逐字对照原图即可；原图 URL 也在同一文件里。

## 为什么这一票值得做（三个理由，缺一不可）

1. **它是 Ticket 10 能否成立的前提**：实测 245 条里 **66 篇是海报扫描图**（`div.conTxt` 里只有 `<img>`）、约 **60 份制度 PDF 是纯扫描件**（无 `/Font`、2.5 MB/份）。补上这两块，语料从 168 篇 / 4.9 万字升到约 300 篇 / **20–30 万字**，而且**恰好包含学籍、奖助、申诉这些学生真会问的内容**——现在这些内容一个字都检索不到。
2. **它同时解开 Ticket 05 的死结**：课表截图识别卡在「模型固定约 11 秒 + 约 86 token/秒，完整课表要 170 秒以上，超过云函数 60 秒上限」。先 OCR 出文字、再走确定性规则或短文本结构化，输出 token 能降一个量级——**这是那条路当前最现实的解法**。
3. **OCR 是赛题点名的能力**：原始赛题的「建议技术实现 → 业务能力」一栏明确列了 **OCR**。做这条链路不是绕路，是补上评分表里的建议能力。

## 决策关卡（需负责人确认）

| # | 事项 | 选项与依据 |
| --- | --- | --- |
| 1 | **OCR 服务选型** | **已定（2026-09-19）**：**腾讯云 OCR**（`GeneralBasicOCR` 通用印刷体识别）。理由：准确率高、支持直接传公网可访问的 `ImageUrl`（**不必先下载 189 张图**），且有现成的 PDF 识别类接口可覆盖第二半。代价：需开通服务与密钥 |
| 2 | **先做哪一半** | **已定（2026-09-19）**：**先做 74 篇图片通知**（单张图、链路短，能最快验证 OCR 质量；不达标就及时止损，不先投 PDF） |
| 3 | **一次性回填还是做增量** | 建议：**先一次性回填**（把已有内容补进库），增量新发的图片通知**先不做自动化**——否则每条新通知都要过一次 OCR，成本与失败处理都翻倍 |
| 4 | **成本上限与密钥纪律** | 189 次调用的量级已测（约 ¥2.8）；需确认是否设月度上限，并沿用既有纪律：**密钥只放环境变量，不进仓库、不进小程序包**（与 `AI_API_KEY` 同一套规矩） |
| 5 | **与 Ticket 05 的关系** | 本票是否顺带把 Ticket 05 的「OCR → 结构化」路径一起验证？还是两票分开、05 自己再决定？（票内倾向：**只为 05 提供 OCR 能力，05 的结构化方案仍由 05 决定**，避免一票两目标） |

## 拟采用的方案（关卡 1 定了再定稿）

```text
一次性回填（本机脚本，离线）：
  图片通知 66 篇 → 下载图 → OCR → 文本 → 写库（标记来源为「OCR 提取」）
  制度 PDF 60 份 → PDF 识别（或转页图）→ 文本 → 写库
增量：暂不自动化；新发的图片通知在库里标记为「正文为图片，未提取」
```

- **输出要与 Ticket 10 的检索口径一致**：正文按段落写入，带 `sourceLabel`，并**明确标记这条正文是 OCR 提取的**——OCR 会有错字，材料与界面上不能把它当成官网原文；
- **失败要留痕**：OCR 失败或置信度低的篇目进缺失清单，不静默丢弃（沿用 `newsSync` 的既有口径）；
- **抽检**：OCR 结果必须人工抽检（按篇抽样比对原图），准确率不达标就不入库。
