# 10：校园通知与办事指引问答（RAG）

**What to build:** 学生用自然语言问校园里的具体事（「户口迁移怎么办理」「返校报到要注意什么」「志愿服务怎么报名」「奖学金公示在哪看」），系统在**已入库的通知与办事指引正文**里检索，给出**带出处的答案**；资料里没有的必须明确说「没检索到」，不得编造。这是本项目第一个真正意义上的 RAG 落点。

**定位（2026-09-19 决定，取代原「校园政策问答」）**：实测发现正式制度（学籍、奖助、申诉）在官网上**没有文字、只有 PDF**（见下），因此本票的承诺范围限定为「**通知与办事指引**」，**不承诺回答正式制度条文**。题库只能从实测可入库的语料里长出来。

**Blocked by:** 01 已合入 main（模型调用、内容安全、三类失败、成本记账全部复用）；07（本票按决策关卡 2 把它的问答入口扩成全校语料，`guardAnswer` 守卫模式一并复用）；**本票自己的前置**——把选定的办事类栏目加进 `newsSync` 并入库（见「前置工作包」）。**不再依赖 Ticket 04 的校园动态 126 页全量导入**（2026-09-19 决定暂缓：它是事后报道）；**但 04 里的团委通知公告 16 页/155 条仍要全量入库**，它属于本票的 A 类主力语料——**这一条是对两处决定的合并解释，需负责人确认**。

**Status:** needs-info（2026-09-19；**前置实现已完成**（8 个栏目接入 `newsSync`、5 项新测试、`npm run typecheck` 通过、`npm test` 306 项全过），**但同日的 PoC 第一轮给出否定结论——官网可入库正文只有 168 篇 / 4.9 万字，其中 97 篇不足 200 字，撑不起这个问答**，见 [语料可行性实测](../../evidence/p6-rag/README.md)。**关卡 1（语料可行性）因此重开**，需在「先做 OCR / PDF 共用链路」「改做校园资讯问答」「砍掉 RAG」三条路里选一条；关卡 2、5 已定（入口 = 并入 07、排期 = 国赛版）；关卡 3（指标口径）随语料决定后再定。**2026-09-26 追加**：本票的检索机制已在**部门域**先行落地（feat/department-activity-rag，见下文「先行落地」一节与 ADR-0002）——验证的是 bigram 检索结构本身，**不改变关卡 1 重开的结论**。)

**来源：** 2026-09-19 比赛加分方向梳理，负责人选定本方向；同一次梳理里，发布路径决定为「**不做认证 / 备案 / 体验版**，P6 用「预览」做真机演示并在材料中如实标注未发布」，该决定已同步 `CONTEXT.md`。

## 为什么这一票值得做

- 评分表里 **AI 能力融合 20%** 的标准原文点名了 RAG，本项目此前完全没有；
- [候选场景对比](../scenario-comparison.md) 对「信息整合」的批评是「**不装 AI 也能看文章，AI 贡献接近于零**」——RAG 问答是唯一能推翻它的形态：**跨上千篇资讯、用一句话找到答案并给出处**，人工翻页做不到；
- 07 部门问答的语料只有 5 个组织、约两千字，**07 票自己也写明了它撑不起这 20 分**；
- 语料**大部分已在数据库里**：`newsSync` 已把校园动态与团委通知公告的正文按段落存进 `news` 集合的 `paragraphs` 字段，新增栏目只需扩展抓取范围、不用另建链路——**但前提是先过语料关**（见下：官网语料分四种形态，能入库的只是一部分）。

## 语料现状（2026-09-19 两轮实测）

两轮实测相继推翻了本票最初的语料假设。**先说结论：官网的语料分成四种形态，只有两种能直接入库。**

| 形态 | 典型栏目（括号内为条数，实测页脚口径） | 能否入库 |
| --- | --- | --- |
| **A. 官网 HTML 正文** | 校园动态 1252、团委通知公告 155、团委焦点新闻 208、学工规章制度 15、学工办事指南 5、学工新闻 31、保卫通知公告 11、保卫服务指南 7、保卫安全管理制度 1、质量监控通知公告 70、教务处教学运行 9、明德书院通知公告 12、知行 5、砺能 1、崇礼资助育人 3、药学院学生动态 133、医学应用技术学院学生动态 13、数字媒体学院新闻 530 | ✅ **直接可入库**（现有解析器已支持两种模板） |
| **B. 正文只有 PDF 附件** | 信息公开网：学籍管理办法 4、奖助贷减免补 12、学生申诉办法 7、学生管理服务 27、毕业生就业信息 11；质量监控政策文件、明德书院通知公告等页面同样只剩「终审：XXX」署名 | ⚠️ **需新增 PDF 文本抽取**（扫描件还要 OCR） |
| **C. 只有公众号外链** | 教务处通知公告 108、电子商贸学院新闻 1075、护理与健康学院新闻动态 712、人工智能学院动态 278、至善书院通知公告 271、笃学书院通知公告 135、弘毅书院通知公告 103、智能制造学院动态、思诚书院通知公告与一站式服务 20、招生通知公告（部分） | ❌ **不可入库**（项目已定「公众号正文不入库」） |

**按内容性质汇总**：**「通知 / 办事指引 / 制度」类 HTML 正文约 300 条**（这是问答最有用的部分）；**新闻与人物报道类约 2150 条**（背景语料，单靠它撑不起政策问答）；**公众号外链约 2700 条**（不可用）；**PDF 制度文件约 60 条**（需新工程）。

### 实测方法与结果（2026-09-19，可复现）

脚本：`scripts/probe-columns.cjs`（只读，遵守官网 ≤1 请求/秒的限速），产物在 `artifacts/corpus-survey/`（该目录已 gitignore）。

1. **教务处通知公告**（第一轮）：第 1 页 `10/11`、第 2 页 `10/11`、第 11 页 `7/9` 条指向 `mp.weixin.qq.com`，**三页抽查 0 条官网详情页**；日期跨度 2023-03 ~ 2026-09，说明**历来如此**。内容恰是学生最关心的（「四六级报名」「国庆中秋放假安排」），但正文全在公众号。→ **2026-09-18「教务处暂缓」的原判断是对的**。
2. **栏目普查**（第二轮，27 个站点 → 513 个候选链接 → 过滤出 96 个内容型栏目 → 抽查 39 个）：`sitemap.xml` 只有 1083 条 URL 且 977 条属于 `/xyxw/*`（连团委 155 条都没收录），**因此 sitemap 只能当弱信号**，判定以逐栏目抓列表页为准。
3. **PDF 形态的确认**（第三轮，抽查正文）：信息公开「学籍管理办法」页面的 `printArea` 里，剥掉脚本与标签后**只剩标题、来源、发布时间、浏览次数**（122 字符），正文由一个 `a[href$=".pdf"]` 经 JS 换成的 `pdfjs` iframe 承载，实测 PDF 路径形如 `/upload/xxgkw/contentmanage/article/file/2024/06/03/202406031537403803.pdf`。→ **制度文件在官网上没有可检索文本**。

### 这对方案意味着什么

- **定位已改**：做的是「**校园通知与办事指引问答**」，不是「校园政策问答」——正式制度在官网上没有可检索文本。
- **PDF（B 类）留作可选加分项**：若日后要纳入，得加 **PDF → 文本** 链路（下载 + 解析 + 失败留痕），扫描件还要 OCR。**不计入当前范围。**
- **产品口径**：题库与宣发都要按实测语料设计，**不能写「跨上千篇通知问答」**。
- **好消息**：A 类里「通知/指南」约 300 条且**恰好是"办事"最需要的**（办事指南、服务指南、规章制度、通知公告），比 1252 条事后报道有用得多。

## 技术约束（决定方案长什么样）

1. **没有向量检索**：现有 `ai` 云函数只实现了两条模型端点（OpenAI 格式 `/chat/completions`、Anthropic 格式 `/v1/messages`，见 `cloudfunctions/ai/providers.ts`），**没有 embeddings 端点**；第三方中转是否支持 embeddings **未实测**。因此首版方案不建立在向量库上。
2. **云函数 20 秒超时 / 256MB 内存**：全量正文在 5MB 量级（按平均 1300 字/篇估算），一次调用读不完也放不下——**必须预建索引**，不能每次查询扫全库。
3. **单次查询有条数上限**（云函数端 100 条量级，实现前以云开发文档为准），索引与召回都要按分页设计。
4. **中文分词**：项目没有分词依赖，也不宜为检索引入一个大依赖；候选做法是 bigram + 停用词，或让模型先把问题转成检索关键词。
5. **两跳调用的时延**：检索 + 生成两次往返，既有成功指标「单次响应 ≤2 秒」在这个形态下不现实（既有端到端冒烟实测，单次模型调用就要 4.6 秒）。
6. **制度文件是 PDF**：信息公开网的学籍、奖助、申诉等办法，页面正文区没有文字，正文由 `a[href$=".pdf"]` 经 JS 换成 pdf.js 的 iframe 承载（实测 PDF 路径形如 `/upload/xxgkw/contentmanage/article/file/2024/06/03/…pdf`）。要么接受「正式制度答不了」，要么新增 **PDF → 文本**链路（依赖要打进云函数包，扫描件还要 OCR）。

## 拟采用的方案（PoC 后定稿）

两段式检索 + 带引用作答：

```text
问题 → 关键词 / bigram 召回 top-N 段落（预建索引） → 模型重排 + 抽取答案
     → 过内容安全 → 返回「结论 + 出处（标题 / 日期 / 栏目 / 原文 URL）」
```

- **复用而非重造**：内容安全适配层、三类失败分类（`model_unavailable` / `content_rejected` / `quota_exhausted`）、成本记账与 50 元/月上限、客户端封装 `services/ai.ts`；
- 无依据时按 07 的口径明确回答「官网未公布 / 没有检索到」，**防幻觉 100%（编造一次即不达标）**；
- 失败降级：AI 不可用时资讯列表与详情仍可正常浏览，文案与 01 的约定一致。

### 部署时要一并确认的一件事：每日增量的请求预算

单次云函数调用最多发 **10 次**页面请求（`MAX_REQUESTS_PER_CALL`，受官网 1.3 秒限速与 20 秒超时约束），分批进度落在状态文档里、中断可续。栏目从 2 个加到 10 个之后，**一次调用可能跑不完一轮每日增量**：

| | 栏目数 | 每日回看的列表页 | 加上新正文 | 需要几批 |
| --- | --- | --- | --- | --- |
| 改动前 | 2 | 6 页（每栏目 3 页） | 少量 | 1 批内可完成 |
| 改动后 | 10 | 约 16 页（只有 1 页的栏目就是 1 页） | 约 10 篇 | **约 3 批** |

定时触发是**每日 06:00 一次**（P3-2 决策⑤，2026-09-18 定）。若一次触发只推进一批，增量会**跨多日慢慢追平**——不会丢数据（每轮都回看最近 3 页），但「每天同步一次」的实际效果会打折。**部署后要看状态文档的进度确认是否跑得完**，跑不完可从三条路里选：① 减少 `INCREMENTAL_PAGES`（例如 3 → 2，把预算留给新栏目）；② 增加一次每日触发；③ 栏目轮转（每天只同步一部分栏目）。**这条不改代码就不算完成，别当成已解决。**

## PoC 第一轮：语料可行性（2026-09-19，**结论否定**）

按「先做 PoC 再投产品面」的建议，先量了语料而不是先写功能。把 9 个拟入库栏目**完整抓下来**（31 个列表页 / 245 条），用**项目自己的解析器**处理，结果：

| 项 | 数量 |
| --- | --- |
| 可用（解析出正文） | **168 篇 / 49,321 字**（平均 294 字） |
| 图片正文（`conTxt` 里只有海报扫描图） | 66 篇（27%） |
| 无正文（只有标题与署名） | 10 篇 |
| 站外（公众号） | 1 篇 |
| **0–200 字的** | **97 篇（58%）** |
| ≥500 字 | 19 篇 |
| ≥1500 字 | 6 篇 |

**结论：按原计划做「校园通知与办事指引问答」不成立。** 语料 4.9 万字、六成篇目不足 200 字，能撑起问答的实质文档只有十几篇，主题还散在挑战杯、台风、户口迁移、校区交通管理上；学生真会问的问题（转专业条件、奖助学金的评审、四六级报名、图书馆开放时间）在这份语料里**基本没有答案**。完整方法与术语见 [语料可行性实测](../../evidence/p6-rag/README.md)。

**这次否定是「花 0 次模型调用买到的」**——长度分布已经足够证伪，不必再花钱测一个撑不起的问题域。PoC 脚本（`scripts/rag-poc.cjs` 的 `crawl` / `recall` / `answer`）已就绪，语料问题解决后可直接复用。

## 建议的第一步：小样本 PoC（不写产品代码）

- **样本**：现有库里已有的文章即可（先跑通机制，不必等新栏目入库）；
- **题目**：10 题有答案 + 5 题跨栏目 + 5 题陷阱（答案不在语料内），逐题记录预期 / 实际 / 判定 / 耗时 / 成本；**题目必须从「预期能力边界」表里的"能答"一栏长出来**（户口迁移、返校指引、志愿服务报名、校园管理规定…），**不要出「四六级报名」这类官网根本没正文的题**——那只会测出"没检索到"；
- **判据**：防幻觉**必须 100%**，否则按 07 的结论处理——一个会编造的问答是负分项，不是加分项；
- **分两轮**：第一轮用**现有语料**验证检索机制本身（召回是否找得到、两跳耗时多少、成本量级）；第二轮等**办事类栏目入库后**再跑一遍，验证「办事类问题」真的答得出来——**第二轮才是决定这个功能价值的那一轮**；
- **产出**：`docs/evidence/p6-rag/` 的报告与原始记录，作为「是否继续」与关卡 3 指标口径的依据。
