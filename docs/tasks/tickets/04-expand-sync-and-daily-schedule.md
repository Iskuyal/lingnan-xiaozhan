# 04：扩大资讯同步范围并启用每日定时

**What to build:** 资讯不再只有「校园动态第一页 10 条」。按负责人选定的栏目与历史范围抓取入库，维护者可手动触发，之后每天自动同步一次；官网内容更新时已有文章被更新而不是产生重复条目，抓取出问题时保留上一次成功的内容。

**Blocked by:** 无。五项范围决策已于 2026-09-18 由负责人确定，结果与依据见 [P3-2 范围表](../p3-2-news-updates.md)：

| 决策 | 结果 |
| --- | --- |
| 首批栏目 | 校园动态 + **团委通知公告**（教务处暂缓：其通知正文多在微信公众号） |
| 历史范围 | 两个栏目全量（校园动态 126 页 / 1252 条，团委 16 页 / 155 条） |
| 增量更新 | 回看最近 3 页，按原文 URL 更新 |
| 请求与预算 | 间隔 1.3 秒、每批 ≤10 页；首次全量约 15 批 |
| 定时 | 每日 06:00，时区 Asia/Shanghai |

**选题理由**：实测校园动态 8/8 无学生行动项（事后报道性质），团委通知公告含公示与通知（真行动项）。依据见 [AI 资讯可行性实测](../../reference/ai-news-poc.md) 5.1 节（来源 Issue #16）。

**Status:** 实现完成、**云端未验证**（2026-09-18）。本票的代码、解析规则、测试与文档已按负责人选定的五项参数在本地完成，`npm run typecheck` / `npm run build` / `npm test`（81 项）通过；**未部署云函数、未触发云端、未跑全量导入**，因此涉及线上数据的验收项一律标为「未验证」，人工步骤见 [云开发文档](../../cloud-development.md#ticket-04-人工步骤)。

**勾选口径：** `[x]` = 本地代码与测试已完成、证据在册；`[ ]` = 仍需云端或人工验证，原因写在条目里。本票不把「本地桩测试通过」当成「云端验收通过」。

**新增模板适配是本票的主要工作量。** 团委通知公告的列表与文章模板**与校园动态不同构**：列表是 `<ul class="newsList">` + `<li>` 直挂 `<span class="date">` 与 `<a title>`（无 `a.tit`），文章是 `<h2 class="title">` + `<div class="property">` + `<div class="printArea">`（无 `h1.title`、无 `div.article-content`、无 PubDate 回退）。实测记录见 [官网资讯栏目与提取记录](../../news-sources.md) 的「通知公告类栏目」一节。

## 两个已实测的硬约束

- **官网限速**：lnc.edu.cn 的 WAF 明写「每秒不能多于 1 个页面请求」，超过会返回 403 并冻结 IP 数分钟以上，且继续重试会延长冻结。**必须按分批多次调用设计**，不能靠调大云函数超时一次抓完。
- **云函数超时 20 秒**（已从默认 3 秒调大）：单次调用能容纳的请求数有限。

## 外链条目（正文不在官网）的处理方式

需求来自实际实测：教务处通知公告首条「勿忘九一八！」的列表条目直接链到 `mp.weixin.qq.com`（见 [官网资讯栏目与提取记录](../../news-sources.md)「通知公告类栏目」）。处理规则与实测证据：

1. **判定**：条目 URL 的主机名不是 `lnc.edu.cn` 或其子域，即视为「正文不在官网」。
2. **动作**：不发起该 URL 的请求（省一次请求，也不违反平台规则），只写入 `title` / `date` / `url` / `sourceLabel` / `capturedAt` / `updatedAt`，`paragraphs` 为空数组；本轮计入 `offsite` 而不是 `failed`，因此不会把整批成功时间压掉。
3. **跳转兜底**：官网页面 302 跳到域外（例如某条站内链接实际指向公众号文章）时，`fetchHtml` 在跟随跳转前就停下并抛 `OffsiteBodyError`，按同一规则只存标题、日期与原文链接，**不抓、不存外链内容**。
4. **已有记录**：外链条目若已有记录，只更新标题/日期/链接，不动 `paragraphs`；已有正文时不会被清空。
5. **测试**：`tests/newsSync-flow.test.cjs` 两项——「正文不在官网的条目只存标题、日期与原文链接，不抓外链正文」（断言从未请求该外链、`paragraphs` 为空、`offsite: 1`、`failed: 0`）与「官网页面跳转到域外时不抓外链正文」（断言跳转目标未被请求）。
6. **未覆盖**：本票纳入的两个栏目（校园动态、团委通知公告）实测第 1 页都没有外链条目，因此真实外链只出现在**暂缓的教务处栏目**；上表两条测试用真实片段改造出外链场景，未在云端遇到过真实外链条目。**此项按「按实际处理并写明方式」勾选，不宣称真实外链条目已入库。**

## 全量导入的批数（与票面估计的差异，需负责人知情）

票面写「首次全量约 15 批」，但那按「每批 10 个列表页」估算，没有计入正文请求；而 1.3 秒间隔 + 20 秒超时下，正文与列表页必须共享同一份 ≤10 次配额（10 次请求 ≈ 13 秒），否则单批必然超时。实际算术：

| 栏目 | 列表页 | 正文 | 请求合计 |
| --- | --- | --- | --- |
| 校园动态 | 126 | 1252 | 1378 |
| 团委通知公告 | 16 | 155 | 171 |
| 合计 | 142 | 1407 | **1549** |

1549 ÷ 每批 10 次 ≈ **155 批**，按 1.3 秒间隔约 34 分钟的实际请求时间（不含网络与写库开销）。本票按已定参数交付（可续跑，进度不丢），**未擅自放宽「每批 ≤10 页」**；若负责人希望减少批数，可选路径与代价见 [云开发文档「未决问题」](../../cloud-development.md#未决问题)。

## 已知取舍与边界

- **增量跳过正文抓取**：增量轮里已有记录的标题与日期与列表页一致且正文非空时，跳过正文抓取（省一次请求，让每日一次调用能覆盖最近 3 页列表）。代价是「官网只改正文、标题与日期都不变」的修改不会被发现；官网补录/改标题会被发现并更新同一记录。若要求正文级一致，需要每次都抓 30 篇正文（≈39 秒），单批 20 秒超时内做不到。
- **失败条目的重试（票面未规定，本票自行决定）**：同一轮内每篇至多重试一次，重试仍失败就放弃并不再重试（失败摘要留在 `sync_state.round.failures`）。理由是首次全量有 1500 多次请求，偶发 HTTP 抖动若不在轮内自愈，就要人工重跑 100 多批去补空洞；`reset` 参数提供了重跑全量的入口（`{"column":"xyxw-xydt","reset":true}`），同样按 URL 幂等。`failed` 因此计的是失败次数，一篇持续失败的条目最多计 2 次。
- **定时触发的来源判定（票面未规定，本票自行决定）**：官方文档给的判据是 `getWXContext().SOURCE === 'wx_trigger'`，定时事件本身还带 `Type: 'Timer'` / `TriggerName` / `Time`；两者都认，任一命中即记为定时触发。判断只影响 `lastTrigger` 等记录，不影响是否执行同步。
- **每日一次与多日完成**：两个栏目各分 5 次请求，若某栏目增量轮要抓的新文章超过 2 篇，该轮会跨多日续跑（游标保存在 `round.page` 与 `pending`），期间 `lastSuccessAt` 不推进。要当天完成需要更大的单批配额（同上「未决问题」）。
- **全量未完成时的定时行为**：`mode: auto` 会继续跑全量（从第 1 页开始、由新到旧），此时不会单独跑增量回看；用户看到的最新内容仍是最新的，因为全量从第 1 页开始。
- **通知公告正文重复标题**：该模板正文常以居中重复的标题开头（公文版式），详情页会同时显示标题与正文首段；属真实页面内容，解析不删。
- **每页条数与页数取自实测页脚**：`columns.ts` 的 126 / 16 是 2026-09-17/18 实测值，官网继续更新后需要上调（未完成前会漏掉新增页；增量回看不受影响）。
- **真机与未登录单页模式**仍未验证（由 [Ticket 08](../tickets/08-post-publish-single-page-mode.md) 跟踪），本票未改变资讯页的读取链路。
