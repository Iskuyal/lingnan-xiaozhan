## 拆分时的三个判断（供回溯）

1. **03 先于 05/06，且不依赖 AI。** Excel 解析是确定性的，先做通就能把「课表数据模型 + 展示 + 周次 + 用户隔离」这套最不确定的部分验证掉；万一 AI 线出问题，课表本身已经能演示。
2. **01 是唯一的 prefactor。** 05/06/07 共用「模型调用 + 内容安全 + 失败降级」，先建一次比三处重复造好。内容安全是微信硬要求，集中在这里而不是散在三票里。
3. **AI 的价值论据在 05、06，不在 07。** 部门问答语料只有 5 个组织、约两千字，撑不起「AI 能力融合」20 分。这一点写在 07 和 09 里，避免将来写材料时误判。

## 与 GitHub Issues 的关系

按负责人要求，这些 ticket **不发到 GitHub Issues**，以本目录的文件管理。仓库里仍开着的 #3–#6 是阶段级粗票，不与之重复；本目录的票落地后可作为它们的执行细目。

状态、依赖和成果更新在各票文件中，并同步本索引；具体操作见 [任务管理约定](../../agents/issue-tracker.md)。`blocked-until-published` 是本地票的发布阻塞说明，不新增 GitHub 分流标签。

**本地票的完成状态用 `done`**：GitHub Issue 用关闭表示任务结束，本地票没有关闭动作，因此用 `done` 表示同一含义——验收达成并挂上成果与证据。`done` 不是 [分流标签](../../agents/triage-labels.md) 的一员，只用于本地票；开工前的分流状态仍只用那五个原始标签。

**本地票的中间状态用 `in-progress`**：代码、测试与文档已完成，但验收依赖人的操作（部署、控制台配置、真机等）而尚未取得云端证据时使用，写成 `in-progress（已完成的部分；待谁做什么）`，并逐条区分「本地已验证」与「云端未验证」——**不把本地桩测试通过当成验收通过**。它既不是完成，也不代表还能重复开工；取得云端证据后按上面的 `done` 收尾，并同步本索引与对应阶段文档。
